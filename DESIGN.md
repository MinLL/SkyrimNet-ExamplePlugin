# SkyrimNet Plugin Examples: Design

Status: draft for review, 2026-10-17. Local only; goes public later.

## Purpose

One repository a mod author clones to build a SkyrimNet plugin. It holds:

- three example plugins of increasing complexity, each buildable and installable on its own;
- the SkyrimNet SDK (C++ API headers, Papyrus API source), synced from Core on every release;
- the modding documentation, moved here from the GamePlugin repo as the source of truth;
- the `/migrate-beta25` agent command.

It replaces the developer kit (`SkyrimNet-<ver>-dev-tools.zip`). The kit's tools
(`content-convert.exe`, `content-validate.exe`) become GitHub Release assets of this repo.

## What the examples teach

| Need | Recommended | Deprecated / avoid |
|---|---|---|
| Papyrus action | YAML in `actions/`, calling a quest-script function | `SkyrimNetApi.RegisterAction` from Papyrus |
| Action category | YAML category file (`customCategory`, no `executionFunctionName`) | `SkyrimNetApi.RegisterSubCategory` |
| Custom decorator | C++ `PublicRegisterDecorator` | `SkyrimNetApi.RegisterDecorator` (a Papyrus VM round trip per render) |
| Mod state in prompts | PapyrusUtil `StorageUtil` + `papyrus_util(...)` decorator | A Papyrus decorator per value |
| Shipping content | External layer `SKSE/Plugins/SkyrimNet/external/{author}.{slug}/` + `manifest.json` | Loose files under `config/` |
| Version check | Papyrus `GetBuildVersion()`; C++ `PublicGetVersion()` + null-checking each pointer | Assuming the API exists |
| Game thread | Worker threads for everything; SKSE task only for engine mutations | LLM, DB, file I/O or heavy work on the game thread |

Each example ships the same way: `dist/<Example>/` is an MO2-installable mod folder
(`<Example>.esp`, `Scripts/*.pex`, `Source/Scripts/*.psc`, `SKSE/...`), zipped by `package.ps1`.

## ESP: Spriggit source, CMake-built

Each Papyrus example keeps its plugin as Spriggit YAML under `spriggit/`. The build turns it
into an ESL-flagged `.esp` with `Spriggit.CLI convert-to-plugin`, the same command Core's
`cmake/Spriggit.cmake` runs. Authors edit in xEdit or the Creation Kit, then serialize back:

```
cmake --build --preset papyrus-only --target ExampleBasics_esp       # spriggit -> .esp
cmake --build --preset papyrus-only --target ExampleBasics_spriggit  # .esp -> spriggit (after editing)
```

Spriggit needs the .NET runtime; `building.md` says so up front and `fetch-tools.ps1` checks for it.

## Example 01: Papyrus basics

Theme: a small "Tavern Manners" pack. Manifest id `example.papyrus-basics`. ESP `ExampleBasics.esp`
with one start-game-enabled quest `ExB_Quest` that holds the action script and a player alias.

```
01-papyrus-basics/
├── README.md
├── spriggit/ExampleBasics/                 Quest ExB_Quest + PlayerAlias
├── scripts/
│   ├── ExB_Actions.psc                     Action functions (quest script)
│   ├── ExB_PlayerAlias.psc                 OnPlayerLoadGame: version check; game events -> SkyrimNet
│   └── ExB_Compat.psc                      Version parsing and the "is SkyrimNet present" check
└── layer/example.papyrus-basics/
    ├── manifest.json
    └── actions/
        ├── tavern_manners.yaml             Category: customCategory, no executionFunctionName
        ├── exb_raise_toast.yaml            Leaf: play idle; static + speaker params
        ├── exb_buy_round.yaml              Leaf: dynamic "target" param, gold eligibility rule
        └── exb_tell_tale.yaml              Leaf: eventString + isShortLived
```

Demonstrates:

- **YAML actions under a category.** One category file plus three leaves, with commented
  `parameterMapping` (`speaker`, `static`, `dynamic`) and `eligibilityRules`.
- **Version check.** `ExB_Compat` first confirms SkyrimNet is installed (`Game.GetModByName("SkyrimNet.esp")`
  before any native call, since calling a native from a missing DLL fails), then parses
  `GetBuildVersion()` and compares it with a `MIN_VERSION` property. On failure: one notification,
  a log line, and the example disables its own features instead of half-working.
- **Pushing events.** The player alias reports gameplay and picks the right call for each, with a
  comment explaining the choice:
  - `RegisterShortLivedEvent`: entering a tavern (scene context, expires);
  - `RegisterEvent`: buying a drink from the innkeeper (recorded, NPCs may react);
  - `RegisterPersistentEvent`: a once-only milestone NPCs treat as established fact.

## Example 02: Papyrus + prompts

Theme: a "Favor Ledger" that tracks favors the player has done for each NPC. Manifest id
`example.papyrus-context`. Requires PapyrusUtil. ESP `ExampleContext.esp`.

```
02-papyrus-context/
├── README.md
├── spriggit/ExampleContext/
├── scripts/
│   ├── ExC_Ledger.psc                      StorageUtil read/write helpers (one place for every key)
│   ├── ExC_Actions.psc                     "Call in a favor" action
│   ├── ExC_EventSchema.psc                 RegisterEventSchema for "example_favor" on game load
│   └── ExC_PlayerAlias.psc                 Records favors from gameplay; fires example_favor events
└── layer/example.papyrus-context/
    ├── manifest.json
    ├── actions/
    │   ├── favor_ledger.yaml               Category
    │   └── exc_call_in_favor.yaml          Eligibility rule on papyrus_util(...) > 0
    └── prompts/submodules/
        ├── character_bio/0650_example_favor_ledger.prompt
        └── user_final_instructions/0650_example_favor_ledger.prompt
```

Demonstrates:

- **StorageUtil as the data store.** Per-actor `int` (favors owed), per-actor `string` (last favor),
  global `StringList` (recent deeds). All keys are prefixed `ExC_` and defined in one script.
- **A custom event type.** `example_favor` registered with `RegisterEventSchema`: typed fields,
  format templates for each mode (`recent_events`, `raw`, `compact`, `verbose`), not ephemeral.
  Fired with `RegisterEvent` when a favor is recorded, so it appears in event history and
  `get_recent_events`.
- **Complex data retrieval in prompts.** The submodules combine
  `papyrus_util("GetIntValue", actor.uuid, "ExC_FavorsOwed", 0)`, `GetStringValue`, `GetStringList`
  on global storage, plus built-ins: `is_in_faction`, `get_actor_value`, `is_in_npc_group`,
  `get_recent_events` filtered to `example_favor`. Each is commented, and each block is guarded so
  that missing data renders nothing instead of an empty sentence.
- **Decorators in action eligibility.** `exc_call_in_favor` is offered only when the NPC owes the
  player a favor, using the same `papyrus_util` decorator.
- **Adding to prompts, not overriding them.** Only submodule files. No base prompt is replaced.

## Example 03: C++ SKSE plugin

Theme: "Native Senses", an SKSE plugin that gives NPCs native-computed context and actions.
DLL `ExampleNative.dll` built on `MinLL/CommonLibVR` (`ng`) through the vcpkg overlay port, one DLL
for SE, AE and VR. Manifest id `example.cpp-native` for its prompt layer.

```
03-cpp-native/
├── README.md
├── CMakeLists.txt, vcpkg.json
├── src/
│   ├── main.cpp                SKSE entry, logging, messaging listener (kDataLoaded -> Bridge::Init)
│   ├── SkyrimNetBridge.h/.cpp  The ONLY file that includes sdk/cpp/PublicAPI.h. FindFunctions(),
│   │                           version gate, a Features struct (decorators, events, queries...)
│   ├── Decorators.cpp          PublicRegisterDecorator: thread-safe reads, "" for invalid actors
│   ├── Actions.cpp             PublicRegisterCPPSubCategory + two PublicRegisterCPPAction leaves;
│   │                           execute marshals engine-mutating calls via SKSE task interface
│   ├── Events.cpp              PublicRegisterEventCallback (+ unregister on shutdown); PublicRegisterEvent
│   └── Worker.h/.cpp           Small worker queue: memory/diary queries never run on the game thread
└── layer/example.cpp-native/
    ├── manifest.json
    └── prompts/submodules/character_bio/0660_example_native_senses.prompt   Uses the C++ decorators
```

Demonstrates:

- **Version gating.** The minimum is API v5 (decorators, event callbacks). Higher-version features
  (v11 audience events, v12 decisions) are enabled only when `PublicGetVersion()` reports them
  **and** the pointer resolved. The log prints which features are on.
- **Decorators.** `example_native_threat` (hostiles near the actor) and `example_native_wealth`
  (gold bracket), used both in the prompt layer and in an action's eligibility rule.
- **Actions.** A subcategory "Native Senses" with two leaves that take JSON params, parse them
  defensively, and return false on bad input.
- **Events.** A callback on `dialogue` that counts conversations per actor (no blocking work in the
  callback), and a native `PublicRegisterEvent` with an audience when the player sheathes their
  weapon near NPCs.
- **Queries.** `QueryMemoriesForActor` on the worker, gated by `PublicIsMemorySystemReady()`.

Known API limitation, called out in the README: C++ decorators take one `RE::Actor*` and return a
string. Multi-argument decorators exist only as built-ins today.

## Agent setup (`.claude`)

Small on purpose. Rules and patterns live in the docs, and the agent files point to them so
there is one copy. No agents, hooks or skills.

**`CLAUDE.md`** (under ~120 lines):
- What the repo is, and which example to start from for which need (a three-row table).
- Build, package and validate commands.
- Hard rules, one line each with the reason, linking to `docs/best-practices.md`:
  - no Papyrus `RegisterAction` / `RegisterSubCategory` / `RegisterDecorator`; use YAML actions
    and C++ decorators;
  - check the SkyrimNet version before calling the API; in C++, null-check every function pointer;
  - nothing slow on the game thread; SKSE task only for engine mutations;
  - in C++, only `SkyrimNetBridge.cpp` includes `PublicAPI.h`;
  - one prefix for every name (scripts, editor ids, StorageUtil keys, actions, decorators);
  - content goes in the external layer; the directory name equals the manifest id; `.yaml` and
    `.prompt` only (case-sensitive, ASCII paths);
  - add to prompts through submodules; never replace a base prompt;
  - `sdk/` is generated; never edit it.
- "Before you finish": build, run `content-validate.exe` on the layer, and if the game is running,
  check actions and prompts through MCP.
- Where to look: `docs/modding/` for content formats, `sdk/` for the API itself.

**`.mcp.json`**: `skyrimnet` → `http://localhost:8889/sse`. It only connects while the game is
running with SkyrimNet loaded. It is the useful path for `get_decorators` (what exists in this
build), `validate_custom_action`, `validate_prompt` and `render_template` against a real NPC.
`CLAUDE.md` says to work without it when the game is off.

**`.claude/commands/new-plugin.md`**: asks for the plugin name, author id and starting example;
copies the example; renames the prefix, manifest id, ESP, quest and script names everywhere; then
builds it. This is the step authors get wrong most often by hand.

**`.claude/settings.json`**: allow-list only: `cmake --build`, `scripts/*.ps1`,
`content-validate.exe`, `git status/diff/log`. Nothing that writes outside the repo.

## SDK sync: Core CI owns `sdk/`

On every Core release (`selfhosted-build.yml`, dispatch with a tag):

1. `utilities/sync_sdk.py` (replaces `bundle_dev_tools.py`) copies the CppAPI headers and the
   SkyrimNet `.psc` sources into `sdk/`, and writes `sdk/VERSION`.
2. It commits this to a branch `sdk/vX.Y.Z` and opens a PR. This repo's CI builds all three
   examples against the new SDK; a break in Core's public API turns that PR red.
3. On merge it tags `vX.Y.Z`. The release workflow uploads `content-convert.exe` and
   `content-validate.exe` to that tag's GitHub Release.

`docs/`, `.claude/` and the examples are **not** touched by sync; they are hand-maintained here.

Needs before it can run: the repo on GitHub (private is fine) and a token or GitHub App with
contents and pull-request write access. Until then `sync_sdk.py --dest D:\repos\skyrimnet-plugin-examples`
runs locally.

## Build order

1. Repo skeleton, tools fetch, CMake modules, docs moved in, `.claude` setup.
2. Example 01 end to end (build, package, install, verify in game).
3. Example 02.
4. Example 03, plus the Core `PublicAPI.h` PR.
5. `sync_sdk.py`, Core CI wiring, gameplugin cleanup (CI push lands once the repo is on GitHub).
